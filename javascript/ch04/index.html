JavaScript Demo — Guide 4: Debugging and Error Handling

1. The Three Error Types — Bug Terminal

🚫 Load-Time (Syntax) Detected as the page loads. The interpreter rejects the code before any of it runs. Caused by misspelled keywords, missing braces, unmatched quotes.
⚙️ Runtime The page loads fine, but the program crashes while trying to execute a specific statement. Caused by calling undefined functions, reading properties of null, dividing by zero.
🧩 Logic The program runs with zero errors reported — but produces the wrong answer. No console message. Only careful analysis reveals the flaw.

2. Strict Mode — "use strict"

Without strict mode, assigning to an undeclared variable silently creates a new global variable — a common source of hard-to-find bugs. Placing "use strict"; at the top of a function (or script) turns that silent mistake into a loud ReferenceError.

Without Strict Mode

The function below assigns to bonusMultiplier without declaring it with let, const, or var. In sloppy mode this silently creates a global variable. No error is ever thrown.

// No "use strict" — undeclared assignment silently becomes a global function applyBonusSloppy(baseScore) { bonusMultiplier = 2; // missing let/const — silently global! return baseScore * bonusMultiplier; }
Click to run.

With Strict Mode

"use strict"; is placed at the very top of the function. Now the same missing declaration causes an immediate ReferenceError — loud and visible, exactly where the mistake is.

// "use strict" turns a silent mistake into a visible error function applyBonusStrict(baseScore) { "use strict"; bonusMultiplier = 2; // ReferenceError thrown here! return baseScore * bonusMultiplier; }
Click to run.

3. Tracing — Trace Station

Tracing means checking a variable's value at a specific point while the program is running. Two common tools: window.alert() pauses execution at each call; console.log() logs silently without interrupting.

Tracing with window.alert()

Each alert() call pauses the program and shows the current value. Click the button — you will see three alerts fire in sequence.

function calcFinalScore(base, streak, rankMult) { window.alert("base: " + base); // trace point 1 let streakBonus = base * streak; window.alert("streakBonus: " + streakBonus); // trace point 2 let final = (base + streakBonus) * rankMult; window.alert("final: " + final); // trace point 3 return final; }

Tracing with console.log() — Open DevTools (F12)

The same function with console.log() instead. All trace values appear together in the Console tab — no interruptions, and the whole loop is visible at once.

Check DevTools console after clicking.

Driver Program — Testing in Isolation

A driver program calls one function with several known inputs and logs the expected vs. actual output. This confirms a function works before it is wired into the full application. Click — then check the console (F12) for the driver output.

Driver output goes to console AND appears here.

Commenting Out Code to Isolate a Bug

If you suspect a section, comment it out and rerun. If the problem disappears, the bug is inside the commented section.

function applyMemberDiscount(total) { // let total = total * 1.08; <-- commented out while isolating bug return total * 0.9; // if the correct result now appears, the bug was above }

4. Debugger Tools — Call Stack Visualizer

The browser debugger lets you pause execution at any line (breakpoint) and step through code one statement at a time. The call stack shows every function currently running, stacked from the outermost call at the bottom to the currently executing function at the top.

Interactive Call Stack Demo

Click each button in order to simulate a 3-deep function call chain. Watch the stack grow as functions are called and shrink as they return.

Click ① to start building the call stack.

Stepping Options — Quick Reference

Step Into (F11) — If the current line CALLS a function, pause INSIDE that function's first statement. Use when you want to trace what a called function does. Step Over (F10) — Run the called function to completion, then pause on the NEXT LINE after the call. Use when the called function is already known to be correct. Step Out (⇧F11) — Run ALL remaining lines in the current function without pausing, then pause where it was called from. Useful when you stepped in by mistake. Resume (F8) — Run until the next breakpoint (or end of script).

Scope & Watch Windows

While paused at a breakpoint, the Scope panel (Sources tab, right side) lists every variable in scope and its current value — updated live as you step. The Watch panel lets you pin specific expressions (e.g. player.score * rankMult) to monitor across many steps without scrolling through the full Scope list.

5. Exception Lab — try / catch / throw / finally

try / catch — Token Submission

The try block attempts the operation. If anything inside it throws an error (built-in or custom), execution immediately jumps to catch. The rest of the page keeps running normally.

Enter a value and click Submit.

throw — Custom Exceptions (Out-of-Range Check)

throw lets you create your own error for conditions JavaScript would not otherwise flag — like a number that is technically valid but out of the allowed business range.

Try values like -5, 0, 25, and 999.

try / catch / finally — Score Save

The finally block runs unconditionally — whether the try succeeded, the catch ran, or even if the catch re-threw. It's the right place for cleanup code that must always execute (closing a connection, resetting a flag, etc.).

Click either button — watch the finally block run.

error.name & error.message — Built-In Error Properties

When a built-in runtime error is caught, the error parameter is an object. Its .name tells you the error category; .message describes what went wrong. Useful for deciding how to respond to different failure types in one catch block.

Click a button to catch and inspect a built-in error.

Since ES10, you may omit the (error) parameter from catch if you don't need to inspect the error — for example when you only want to display a generic fallback message.

6. Global Error Handler — window.onerror

Individual try/catch blocks protect specific sections of code. The window.onerror event fires for any uncaught error anywhere on the page — useful as a last line of defense and for logging errors to a server.

Setting Up the Global Handler

// Assign a handler function to the window's onerror event property. // It receives 5 parameters: message, source file, line, column, error object. window.onerror = function(message, source, lineNumber, colNumber, errorObj) { console.log("Error on line " + lineNumber + ": " + message); return true; // true = "I handled it" — suppress browser default reporting // false = "help me out" — browser ALSO logs its default message };
Click ① to install the handler, then ② to trigger an uncaught error.

addEventListener Alternative

// The event-listener style — allows multiple independent handlers: window.addEventListener("error", function(event) { console.log("Caught via listener: " + event.message); });

Best Practices Checklist

  • Enable "use strict"; at the top of every script — it catches an entire class of silent mistakes before they become runtime surprises.
  • Test every function individually with a driver program before wiring it into the full application.
  • Wrap any code that depends on user input inside a try/catch — users will always find ways to submit values you didn't expect.
  • Use console.log() rather than window.alert() for routine tracing — alerts are cumbersome inside loops and block the whole page.
  • Re-test the entire program after fixing any bug — statements depend on each other, and fixing one thing can silently break another.
  • Remove all temporary tracing code (alerts, console logs, commented-out lines) once debugging is complete — shipping trace code is a common oversight.
